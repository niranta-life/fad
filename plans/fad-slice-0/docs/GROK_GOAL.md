/goal Build Federated Agent Directory (FAD) Slice 0: a secure, production-grade backend foundation, with a real Node.js/TypeScript API, PostgreSQL persistence, offline organization/credential administration, a TypeScript SDK, and container deployment.

PRODUCT CONTEXT
FAD is the control plane for an eventual federated enterprise agent directory: agent identities, versioned capabilities, governed tags and policies, discovery, delegation, verification, revocation, federation and MCP. This goal is ONLY the foundation. Future slices must be able to add features without breaking /v1 APIs. Do not implement agent registration, tags, MCP, federation, OAuth, agent runtime invocation, a UI or general-purpose user registration.

SOURCE OF TRUTH
Read the attached Slice 0 package: {pwd}/plans/fad-slice-0/docs/SPECIFICATION.md, {pwd}/plans/fad-slice-0/contracts/openapi.yaml, {pwd}/plans/fad-slice-0/migrations/0001_foundation.up.sql, {pwd}/plans/fad-slice-0/deploy/postgres/00_roles.sql, {pwd}/plans/fad-slice-0/migrations/ROLLBACK.md, {pwd}/plans/fad-slice-0/sdk/SDK_CONTRACT.md, {pwd}/plans/fad-slice-0/verification/TEST_MATRIX.md, {pwd}/plans/fad-slice-0/docs/SLICE1_HANDOFF.md, and {pwd}/plans/fad-slice-0/deploy/OPERATIONS.md. Reconcile with existing repository architecture and published API contracts. Preserve the Slice 1 assumptions documented in {pwd}/plans/fad-slice-0/docs/SLICE1_HANDOFF.md. Do not silently replace or fork any existing identity/tenant/audit/idempotency system. If a reference artifact has an implementation error, correct it with an ADR and contract checks before writing app code.

REQUIRED STACK AND ARCHITECTURE
- Node.js supported LTS, strict TypeScript, Fastify or existing compatible HTTP framework.
- PostgreSQL 16+ authoritative storage; migration runner with atomic version/checksum tracking and exclusive migration lock.
- REST HTTP GET /health/live, GET /health/ready, GET /v1/organizations/current; OpenAPI 3.1 source of truth. No mock responses.
- X-FAD-API-Key header for protected requests. Key generated by an offline, privileged CLI, not HTTP endpoint. API never chooses tenant based on caller-supplied org id.
- Organization, principal, API credential, immutable audit and idempotency tables. Reuse exact contracts in package.
- Org- and principal-scoped authentication, active checks, exact scoped permission organizations:read; future Slice 1 scopes provisionable without exposing agent routes.
- Strong entropy credential, HMAC-SHA256 at rest with secret pepper from secret store, opaque kid lookup, timing-mitigated comparisons, disabled/revoked/expired handling, key rotation.
- Strict tenant isolation using SQL organization predicates + transaction-local fad.org_id + FORCE RLS. API role fad_app is non-owner, no BYPASSRLS, no DDL, no direct SELECT on api_credentials. Use a narrowly scoped hardened SECURITY DEFINER function for pre-tenant credential lookup.
- Stateless HTTP replicas, JSON request/error envelopes, structured logs and request IDs, readiness/liveness, timeouts, graceful shutdown, rate limiting and telemetry. Never log secrets.
- Commit security-sensitive admin mutations and audit entries in a single DB transaction. Build idempotency infrastructure for Slice 1 but do not expose unused public endpoints.
- OCI multi-stage container build, non-root runtime, reproducible dependency lock and build, Docker Compose local stack. Real migrations via separately privileged job, not on API startup.
- Implement @fad/sdk TypeScript network client for health.live(), health.ready(), organizations.current(), typed errors, deadlines, cancellation and bounded safe GET retries.

USER JOURNEY (MUST WORK END TO END)
1. Provision a clean Postgres and apply audited DB roles, then migration.
2. Through offline fad-admin CLI, create Organization A and Organization B.
3. Create one service principal per organization; issue independent organizations:read scoped API keys. Reveal secrets only at issuance.
4. Start one API container, then two stateless replicas; use GET /v1/organizations/current with key A and key B. Each returns ONLY its bound organization.
5. Call with invalid, malformed, unknown, missing, expired, revoked key; each receives safe 401. Valid insufficient-scope key receives 403.
6. Send Org A key plus X-Organization-Id for Org B and query selector; neither can return Org B. Unknown query selector returns 400.
7. Revoke old A key after issuing successor; successor works and revoked key fails on ALL replicas.
8. Verify stable state after container restart; simulate DB outage to prove 503 readiness/authenticated calls; restore DB and verify recovery.
9. Install @fad/sdk in a separate Node project, query current organization, verify error and cancellation handling.

G. Implement @fad/sdk network client with package smoke test from a separate project. Do not implement future agent SDK methods.

API CONTRACT / INVARIANTS
- Success {data,meta:{request_id,api_version:'v1'}}. Error {error:{code,message},meta:{request_id,api_version:'v1'}}. Health separate: {status:'ok'|'ready'|'not_ready'}.
- Auth header X-FAD-API-Key. GET /v1/organizations/current needs organizations:read. Health routes unauthenticated, no sensitive fields.
- No response may contain key, digest, pepper or cross-tenant identifying information. Auth failures are generic 401, insufficient scope 403, DB required dependency unavailable 503.
- RLS always fails closed without fad.org_id; transaction and DB connection context cannot leak into pooled requests.
- Principals(organization_id,id) unique is required for next-slice FK. Runtime DB role fad_app has no BYPASSRLS.
- Storage of credential fingerprint only, scopes explicit. No wildcard scope. Audit security mutations transactionally.
- Unknown org selectors must be ignored only if harmless non-contract headers; query selectors are invalid 400. Never allow org switching.
- Production startup must reject missing pepper, missing DB, unsupported/missing migrations and insecure non-TLS ingress configuration where detectable; behind TLS reverse proxy deployment contract must be documented and enforced at ingress.
- No breaking change to existing /v1 contract; use an OpenAPI backward-compatibility diff check.
